# How to Compare Python Email and SMS API Providers — Transactional Report Attachments

Send the generated healthtech report through a deterministic attachment builder, then compare transactional event notifications across email and SMS API providers by the work needed to preserve that artifact and explain its delivery state.

The deciding constraint is integration effort: a successful text notification doesn't establish that the recipient received the intended report attachment.

Short answer: freeze the report bytes, build a synthetic MIME fixture, and evaluate each candidate against the same attachment and status requirements. Keep SMS as a separate, minimal notification path. For US and EU deployments, record the locations and contractual boundaries that actually apply to each path before choosing an integration. A low advertised send price cannot answer those questions.

This experiment note proposes a repeatable test; it reports no provider benchmark. Its evaluation constraint is narrow: recover the exact generated bytes from an email without invoking the model again. That gives a Python AI application builder a useful notebook-to-prod boundary, with prompt-cost aware retries and an eval-driven handoff into messaging. Teams migrating a Node.js notification worker can use the same artifact contract; the runnable fixture here stays in Python.

## How should we compare transactional email and SMS API providers for report notifications?

A healthtech report starts as an application artifact.

Turning it into an email adds a filename, a media type, transfer encoding, recipient routing, and a submission lifecycle. Those details deserve their own evaluation. A fluent generated summary tells you little about whether the attachment survived serialization.

The tempting shortcut is to regenerate the report inside the notification retry and put its text directly into a message. That combines two independently changing operations: generation and dispatch. For this workflow, choose a frozen artifact instead. Retrying delivery should reuse its bytes; generating a revised report should create a new artifact version. This is a proposed application invariant, not a claim that any transport supplies it automatically.

Keep bytes stable.

Email and SMS solve different parts of this job. Email can carry a MIME attachment; treat SMS here as a short notice directing the recipient into the application's authenticated report workflow. Don't copy clinical content into the SMS template merely because the report is available in memory. The paths need separate acceptance criteria, and neither path's delivery status demonstrates that a person reviewed the report.

## Step 1: Freeze a synthetic report and round-trip the attachment

Start with invented fixture data and the Python standard library. The example uses a plain-text report so its bytes remain inspectable. It exercises MIME construction and parsing locally; it cannot test inbox placement. For a PDF-producing application, substitute an actual synthetic PDF artifact and its correct media type before comparing transport integrations.

Run this as one Python script. Its assertions check attachment count, filename, media type, and recovery of the original bytes.

```python
from email import policy
from email.message import EmailMessage
from email.parser import BytesParser
from hashlib import sha256

report_id = "synthetic-report-0042"
report_bytes = (
    "Synthetic report: 0042\n"
    "Generated narrative fixture; no patient information.\n"
).encode("utf-8")
expected_digest = sha256(report_bytes).hexdigest()
filename = f"{report_id}.txt"

message = EmailMessage(policy=policy.SMTP)
message["From"] = "reports@example.invalid"
message["To"] = "recipient@example.invalid"
message["Subject"] = "Your synthetic report"
message.set_content("The synthetic report is attached.")
message.add_attachment(
    report_bytes,
    maintype="text",
    subtype="plain",
    filename=filename,
)

wire_bytes = message.as_bytes()
parsed = BytesParser(policy=policy.default).parsebytes(wire_bytes)
attachments = list(parsed.iter_attachments())
assert len(attachments) == 1
attachment = attachments[0]
recovered = attachment.get_payload(decode=True)
assert attachment.get_filename() == filename
assert attachment.get_content_type() == "text/plain"
assert recovered == report_bytes
assert sha256(recovered).hexdigest() == expected_digest
print({
    "report_id": report_id,
    "artifact_bytes": len(report_bytes),
    "message_bytes": len(wire_bytes),
    "round_trip": "passed",
})
```

The example deliberately leaves out a provider adapter.

Ask each candidate to demonstrate its supported attachment input, then add that conversion at a single boundary. Measure the effort to implement and maintain it, including its error path. The local round trip gives you a fixture to reuse; only a controlled send and examination of the received message can test the next boundary. The trade-off is extra artifact storage and lifecycle management in exchange for repeatable dispatch. This design is not suitable for reports whose approved delivery policy excludes attachments; use the authenticated report-access workflow in that case. The limitation of the fixture is equally specific: it tests serialization, not the provider's API or receiving mail server.

There's a concrete size trap here. RFC 2045 encodes three input octets as four base64 characters, with padding for incomplete groups; line wrapping and MIME headers add further bytes. Raw report size therefore cannot represent serialized message size. For each candidate, verify what its documented limit counts and test a synthetic artifact near that boundary. Don't invent a universal attachment ceiling.

## Step 2: Compare the work around the payload

Use the same synthetic report, recipient setup, and expected state transitions for every candidate. A comparison of transactional email and SMS APIs becomes useful when it exposes implementation work that a happy-path send hides. Keep a small record of the following questions, with a primary documentation reference or a controlled test result beside each answer.

For a shortlist containing SendGrid, Postmark, and Mailgun, maintain three separate evidence records. Do not transfer a verified attachment limit, regional commitment, or retry guarantee from one record to another. This note establishes no product-specific feature ranking; those boundaries remain unverified until the comparison collects the evidence.

| Boundary | Evidence to collect | Integration work to count |
| --- | --- | --- |
| Email attachment | Accepted payload shape, size definition, received filename and bytes | Serialization, validation, fixture maintenance |
| Submission outcome | Meaning of acceptance, rejection, and ambiguous timeout | Durable state and reconciliation logic |
| Event feedback | Event definitions, authentication, replay behavior | Verification, deduplication, state mapping |
| SMS notice | Destination support and applicable sender requirements | Separate templates, sender setup, status handling |
| US and EU operation | Documented processing locations and contractual scope | Deployment configuration and review effort |

Leave an unanswered item marked unverified.

A region label on an endpoint is insufficient evidence for the location of every downstream operation; request the relevant scope rather than inferring it. Evaluate US and EU SMS destinations separately against the sender requirements documented for those destinations. This is a verification method, not a statement that all jurisdictions share one rule.

Keep the report identifier and artifact version in application state. If submission times out, preserve an unknown outcome until the adapter can reconcile it using documented mechanisms. A blind retry may create another message; an adapter cannot promise exactly-once delivery merely because the application has a stable report identifier. When a provider documents idempotency, test its scope and retention period instead of assuming the feature covers every retry.

That is where integration effort hides in this proposed comparison: each undocumented state becomes something the team must resolve before operating the workflow confidently. Record actual engineering time during the trial, plus the number of candidate-specific branches retained afterward. Don't turn those measurements into a fabricated score before running the trial.

## Step 3: Measure the handoff before copying the design

Move from the notebook fixture to a worker that reads an approved artifact and submits it through the adapter. Keep generation evaluation separate from transport evaluation. The generation suite should assess the report against approved synthetic cases; the transport suite should assess attachment identity and state handling.

An intact attachment isn't evidence of clinical correctness.

For prompt-cost aware operation, record generation usage per artifact version and verify that notification retries do not invoke generation again. Measure message size, attachment round-trip success, ambiguous submissions, duplicate processing, and time spent integrating each candidate. Use synthetic content in traces, and avoid putting report bodies or recipient details into routine debug logs. Choose thresholds from the application's requirements before collecting results.

Authentication and engagement need separate checks as well. DMARC evaluates alignment involving the visible From domain and authenticated identifiers; it does not validate attachment contents or establish that an email was read. Apple's Mail Privacy Protection can prevent senders from learning whether a message was opened. An open event is therefore a poor completion criterion for this report workflow. Prefer a defined application event for authenticated report access, while recognizing that access alone doesn't establish comprehension.

Before adopting this design, run the serialized fixture through a controlled mailbox, exercise rejection and ambiguous submission, and check how the SMS path behaves when email fails. Record what remains unverified. The useful comparison result is a defensible account of attachment fidelity and integration effort across the required destinations, supported by observed behavior. Price can remain a budget constraint without becoming the evidence for correctness.
